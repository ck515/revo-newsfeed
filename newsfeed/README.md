# REVO ニュースパイプライン

```
collect (RSS) → screen (機械的除外) → score (Claude API) → 候補5件
      → 【人が選択：Discord】 → カード生成 → Discord納品
      → 【人が投稿：Meta Business Suite】
```

**人のゲートが2つあり、どちらも必須です。** どの記事を出すかの選択と、生成されたカードの承認。自動投稿は一切ありません。Instagram Graph APIを使わないので App Review が不要で、誤投稿が構造的に起こりません。

```
newsfeed/
├── config.py        … RSSソース、除外キーワード、上限値
├── collect.py       … RSS取得・正規化・重複排除
├── screen.py        … 機械的除外
├── score.py         … 採点プロンプト、APIコール、出力契約の検証
├── deliver.py       … カード生成、Discordメッセージ組み立て
├── pipeline.py      … オーケストレーション
├── fixtures/        … テスト用データ
└── state/           … 既読ID、日次スナップショット
```

## 依存

```bash
pip install feedparser anthropic
# カード生成側: pip install playwright budoux && playwright install chromium
```

`ANTHROPIC_API_KEY` が必要（`--live` 時のみ）。

## 実行

```bash
# fixtureで通し実行。ネットワーク不要、APIキー不要
python pipeline.py --approve-top 3 -v

# 収集と除外のみ。まず1〜2週間これを回して流量を把握する
python pipeline.py --live --no-score

# 本番
python pipeline.py --live
```

フィルタや採点プロンプトを編集したら、必ず fixture で通してから `--live` に上げてください。

`--strict` を付けると出力契約の違反で中断します。cron で回す場合は付けておく方が安全です。

## テスト結果（2026-08-17、実ニュース23件）

実際の2026年8月の国内自動車ニュースから fixture を作成し、除外されるべき記事を混ぜて検証しました。

**機械的除外: 23件 → 通過14件 / 除外9件**

| 理由 | 件数 | 例 |
|---|---|---|
| harm | 1 | 高速道路の多重事故（死亡） |
| defect | 3 | リコール届出、サスペンションキットの溶接不具合 |
| offtopic | 3 | EV補助金の見直し、販売台数統計、商用軽バンの改良 |
| foreign_market | 2 | 北米向けキックス、インドのブレッツァ |

投稿してはいけない記事はすべて機械的に落ちました。

**採点: 14件 → 閾値6以上が8件 → 提示5件**

採点層が拾ったもの: GRセリカ復活（10点）、KUHL大感謝オフ会（9点）、BLITZのプレリュード用パーツ（8点）。

採点層が落としたもの: ミニ四駆の新製品（0点）、販売動向のコラム（2点）、メルセデスGLA（2点）、実用SUVの改良（3点）。

**キーワードで落ちない無関係記事は、採点層が拾って落とす**という二層構造が意図通り機能しました。ミニ四駆記事は除外キーワードに一切触れないので、機械的除外だけでは通過します。

## 検証中に見つけて直したバグ

**1. 「トラック」が広すぎた**
`商用車` の除外に `トラック` を入れていたため、「ピックアップトラック」に反応してタンドラの国内正規販売のニュースが落ちました。愛好家向けには十分価値のある記事です。商用車の語は `軽トラ` `商用バン` `ハイエース` など具体名に限定しました。

**2. 曜日のマッピングが1日ずれていた**
`POST_WINDOWS` のキーを {1,2,3} = 火水木のつもりで書いていましたが、`date.isoweekday()` は月曜が1なので実際は月火水でした。出力を見ても気づけない種類のバグです。{2,3,4} に修正済み。

**3. 上限に当たった投稿が無言で捨てられていた**
1日1本の上限を `deliver.build()` の中で `continue` で処理していたため、3件承認しても2件しか出力されませんでした。承認済みの投稿が消えるのは最悪の挙動です。枠の確保を `next_windows()` に移し、上限に当たったら翌日に回すようにしました。枠が足りない場合は例外で止まります。

**4. 出力契約に矛盾があった**
「5つのカテゴリから1つ選ぶ」と「どれにも当てはまらなければ低得点」が両立していませんでした。無関係な記事にも無理にカテゴリを付けさせることになります。閾値未満の記事は `category: null`、`headline: ""` を許容するように契約を修正しました。

## 日次レビュー（Discord）

その日の候補は1通のメッセージにまとまってDiscordに届きます。日付・曜日と、収集→除外→候補の件数を先頭に置いてあるので、後からDiscordを遡っても「いつのバッチか」が分かります。

```
# 📅 8/18(火) のニュース

`収集 23件 → 除外 7件 → 候補 8件`

**1️⃣　10点　DEBUT**
GRセリカ復活が確実視、ポルトガルでテスト走行
-# 最新自動車情報 ・ スポーツカー復活、最関心事
-# https://...

**7️⃣　7点　DEBUT**　🌍 海外 ・ 🎬 公式動画
ランボルギーニが新型モデルを発表
...

──────────
数字でリアクション → カード生成 ／ ⏭ 全スキップ
-# 除外内訳: defect 3・harm 1・offtopic 3　｜　投稿枠 2026-08-18 19:00
```

候補ゼロの日も「本日は候補なしです」というメッセージが届きます。**沈黙しないのが重要**で、何も来ない日があると、候補がないのかパイプラインが壊れたのか区別が付きません。

2000字を超える場合はアイテム境界で分割されます（実測では候補9件で964字なので、通常は1通に収まります）。

## 上限値

Autopilotが自己増殖で暴走した経緯があるため、以下は設定値ではなく定数です。

```
MAX_CANDIDATES_PER_DAY = 8   # 人に見せる上限（Discordの数字リアクションが10までなので余裕を持たせた値）
SCORE_THRESHOLD        = 6
POST_WINDOWS           = 平日 19:00 / 土日 21:00
```

**投稿本数の上限は撤廃しました。** 残っているのは「人に見せる候補の上限」だけです。レビューリストが長すぎると読まれなくなる、というのがここで防ぎたい失敗です。

投稿枠は毎日あります。週末は21時で、平日より遅いのは週末の夕方がユーザーの外出時間帯だからです。

## 海外ニュース

海外ニュースは**除外せず、マーカーを付けて採点対象にします。** 以前は `foreign_market` キーワードで機械的に落としていましたが、ランボルギーニの新型発表のように国内の読者も見るニュースまで消えていました。

キーワードが判断できるのは「海外の話かどうか」までで、「この読者に刺さるかどうか」は判断できません。後者は採点層の仕事です。

- `screen.py` が `region_hint` を付ける（`JP` / `WORLD`）
- 採点が `region` を返す。返らない場合は `region_hint` にフォールバック
- Discordのリストで 🌍 海外 として表示

他市場専用の実用車（インド専用SUVなど）は採点で低得点になり、自然に落ちます。

## まだできていないこと

**RSSのURL検証** — `config.py` のフィードURLは未検証です。この環境からは外部ネットワークに到達できませんでした。`--live --no-score` を1回回して、0件のソースを潰してから本番に入ってください。

**採点プロンプトの実運用検証** — 今回の採点は手動で契約通りに実行したもので、API経由での挙動は未確認です。最初の1〜2週間は `--no-score` で流量を見て、その後 `--live` に切り替えてスコアの妥当性を目視してください。スコアと理由をDiscordに必ず表示させ、感覚とずれていたらプロンプトを直す期間として扱ってください。

**選択・非選択の記録** — 選ばなかった候補を残す仕組みが未実装です。Notionに候補DBを作ると、採点プロンプトの改善材料になり、ニュースが少ない週に過去候補から拾えます。

## Discord連携

常駐プロセスは不要です。リアクションの読み取りはGateway接続ではなくREST APIでできるので、**GitHub Actionsの1日2回実行で完結**します。

```
19:00        run_review.py    その日の候補リストを投稿し、数字リアクションを付ける
19:00-24:00  check_picks.py   5分おきにリアクションを確認
             ↓ 押されていれば
             run_publish.py   カードを生成して添付
```

**番号を押せば最大5分で届きます。** ターミナルに戻る必要はありません。

### 5分おきでも実行時間を食わない理由

`check_picks.py` は `requests` だけで動きます。レンダラーもPlaywrightも読み込みません。リアクションが無ければ十数秒で終了します。

Playwrightとブラウザのインストール（2〜3分）が走るのは、**押されている日の押された回だけ**です。ブラウザはキャッシュされるので2回目以降はさらに短くなります。

1日60回走っても、実際に重い処理が動くのは配信する1〜3回だけです。

### check_picks の判定

| 状況 | 結果 |
|---|---|
| その日のレビューが無い | 起動しない |
| 候補ゼロ | 起動しない |
| リアクション無し | 起動しない |
| ⏭（全スキップ） | 起動しない |
| 押されているが全て配信済み | 起動しない |
| 未配信の選択がある | **起動する** |

### 既存のAutopilot Webhookを流用します

投稿は Autopilot が使っている `DISCORD_WEBHOOK_URL` をそのまま利用します。新しい投稿用の認証情報は不要です。

**botが必要なのはリアクションの部分だけです。** Webhookは投稿はできますが、誰がリアクションしたかを読めません。読み取りには認証付きトークンが要るので、botが数字リアクションの付与と読み取りを担当します。

投稿はWebhook（Autopilotの名前とアイコンで表示）、リアクションはbot、という分担です。Webhookが投稿したメッセージにも、同じチャンネルにいるbotならリアクションを付けられます。

`DISCORD_WEBHOOK_URL` を設定しない場合は、botが投稿も行います（その場合は `DISCORD_CHANNEL_ID` が必要）。

### botの作成

1. https://discord.com/developers/applications → New Application
2. Bot → Reset Token でトークンを取得
3. OAuth2 → URL Generator で `bot` スコープ、権限は **Add Reactions / Read Message History** のみ
4. 生成されたURLを開き、Autopilotが通知しているサーバーに招待
5. そのチャンネルでbotが閲覧できることを確認

権限は最小限で足ります。投稿はWebhookが行うので Send Messages すら不要です。

### GitHub Secrets

| Secret | 取得元 | 備考 |
|---|---|---|
| `DISCORD_WEBHOOK_URL` | **Autopilotの既存値をそのまま** | 別チャンネルにしたい場合のみ作り直し |
| `DISCORD_BOT_TOKEN` | Developer Portal → Bot → Token | 新規 |
| `DISCORD_BOT_USER_ID` | `python -c "from discord_client import Discord; print(Discord().me()['id'])"` | 新規 |
| `ANTHROPIC_API_KEY` | Anthropic Console | Autopilotの既存値でよい |

`DISCORD_CHANNEL_ID` は不要です。Webhookの応答から自動で取得します。

`.github-workflow-news.yml` を `.github/workflows/news.yml` に配置してください。

### 接続確認

```bash
python -c "from discord_client import Discord; Discord().doctor()"
```

投稿経路、botのID、`DISCORD_BOT_USER_ID` の一致を確認し、テストメッセージを1件投稿してリアクションを付けます。表示されるコマンドで、手動リアクションが正しく読めるかまで確認できます。

### 送信せずに確認する

```bash
python run_review.py --date 2026-08-18 --dry-run
python run_publish.py --date 2026-08-18 --dry-run --pick 1,7
```

`--dry-run` は実際のHTTPリクエストのURLとペイロードを表示するだけで、Discordには何も送りません。`--pick` はリアクションの代わりに番号を直接指定するテスト用オプションです。

### 再実行しても二重投稿しない

配信済みの記事IDは `state/review-<日付>.json` に記録され、次回は自動でスキップされます。GitHub Actionsが失敗して再実行しても、既に送った分は送られません。追加で選び直した分だけが配信されます。

### 状態ファイル

`state/` の中身は実行間で保持される必要があります。

- `seen.json` — 既読の記事ID。消えると毎朝すべての記事が新規扱いになります
- `review-<日付>.json` — メッセージID、候補リスト、配信済みID

ワークフローは実行後に `state/` をリポジトリにコミットします。プライベートリポジトリで運用してください。

### botの自己リアクションについて

botが数字リアクションを先に付けておくのは、ckがタップするだけで済むようにするためです。そのため選択を読むときは**bot自身のリアクションを除外する必要があります**。`DISCORD_BOT_USER_ID` が未設定だと全項目が選択済みに見えるので、必ず設定してください。

## カードの背景

`config.py` の `CARD_BACKGROUND` で3つから選びます。

| 値 | 動作 | 権利 |
|---|---|---|
| `none` | 文字のみ | リスクなし |
| `category` **（既定）** | `cards/backgrounds/<カテゴリ>.jpg` を固定で使う | 自前素材なのでリスクなし |
| `article` | 記事のOGP画像をフィードから取得して使う | **媒体が制作した写真** |

`category` を既定にしています。`cards/backgrounds/` に `DEBUT.jpg` `PARTS.jpg` `EVENT.jpg` `RACE.jpg` `RETRO.jpg` を置くと自動で割り当てられます。**ファイルが無いカテゴリは文字のみにフォールバック**するので、1枚ずつ足していけます。

同梱しているのは仮の素材です。大黒や辰巳で撮った夜景など、ck自身が撮影したものに差し替えてください。記事内容とは無関係でも、カテゴリごとの雰囲気が出ていれば十分機能します。推奨は縦長（1080×1350以上）、暗めの画像です。

`CARD_OVERLAY`（既定 0.42）で黒オーバーレイの濃度を調整できます。明るい素材なら 0.55 まで上げてください。

### `article` を既定にしていない理由

フィードから取れる画像は媒体が撮影・制作したものです。このアカウントの運用ルールでは、使用可能な写真をメーカー公式・パーツメーカー公式・イベント主催者提供に限定しています。`article` はその線引きを越える選択なので、**継承された既定ではなく明示的な判断であるべき**という理由で `category` を既定にしました。

使う場合は `CARD_BACKGROUND = "article"` に変更してください。画像の取得に失敗した場合は文字のみになります。

## 見出しと背景の差し替え

モデルが書いた見出しは下書きで、自動で入る背景は当て推量です。どちらも**Discordを離れずに直せます。**

候補リストのメッセージに**返信**する形で、カード番号を先頭に書きます。

```
3                        画像を添付 → 3番の背景になる
3 筑波1分6秒台のケンメリ    → 3番の見出しを差し替え
3 新しい見出し + 画像添付   → 両方
```

返信でないメッセージは読まないので、チャンネルの雑談が指示と誤認されることはありません。同じ番号に複数回返信した場合は、**後の返信が勝ちます**。

手で渡した画像は、`CARD_BACKGROUND` の設定より優先されます。意図して選んだものなので、自動判定より強くしています。

画像以外の添付（PDFなど）は無視されます。番号が候補の範囲外なら警告を出してスキップします。

差し替えを読まずに配信したい場合は `--no-overrides` を付けてください。

### コマンドラインから指定する

手元で作り直すときは `--title` の方が早いです。

```bash
python3 run_publish.py --pick 1,3 \
  --title "1=筑波1分6秒台を出すケンメリの中身" \
  --title "3=富士で開催される大規模オフ会"
```

番号は候補リストの番号です。複数回指定できます。**コマンドラインの指定はDiscordの返信より優先されます** — 目の前にカードがある状態で今打ったものなので。

書式が違う場合や番号が範囲外の場合は、その場でエラーになります（黙って無視されません）。

## 背景透過PNG

配信されるカードは毎回2枚です。

| ファイル | 用途 |
|---|---|
| `01_xxxx.png` | そのまま投稿できる完成版 |
| `01_xxxx_overlay.png` | **背景透過PNG**。編集ソフトで好きな写真を下に敷く |

透過版はタグ・見出し・ルール・ハッシュタグ・フッターだけが残り、背景は完全に抜けています（RGBA、アルファ0）。Photoshopで写真の上に重ねれば、レイアウトを組み直さずに背景付きカードが作れます。

自動で入る背景は所詮当て推量なので、**実質的にはこちらが本命**です。パイプラインが担当するのは文字組みまでで、絵は人が選ぶ、という分担になります。

単体で作る場合:

```bash
cd cards
python3 render.py --headline "見出し" --category DEBUT \
  --keywords GRセリカ トヨタ --date 2026-08-18 \
  --transparent --out out/overlay.png
```

透過モードでは `photo` 引数は無視されます。どうせ差し替えるものなので。

## 本文の自動生成

キャプションの本文は、**選ばれた記事だけ**を対象に配信時に生成します。採点時に全件分を書くとほとんど捨てることになるので、後段に置いています。

生成時には記事ページを取得して本文を渡すので、RSSの短い要約からではなく実際の記事内容から書かれます。

```
GRセリカ復活が確実視、ポルトガルでテスト走行     ← 見出し

トヨタがセリカの名を「GRセリカ」として復活させる    ← 生成された本文
見通しとなった。ポルトガルでテスト車両が確認されて
おり、開発は最終段階とみられる。…

出典: 最新自動車情報                          ← 定型
REVOでは全国のカースポットとイベントを…
```

### 以前の実装を変えた理由

これまでは**RSSの要約を120字切り出してそのまま貼っていました**。他媒体が書いた文章の転載になるので、continuing するべきではありませんでした。生成に切り替えたのはそのためです。

プロンプトには「元記事の文章をそのまま使わない」「記事にないスペックや価格を創作しない」の両方を入れています。前者だけだと転載を避けようとして事実を捏造する方向に逃げるので、両方必要です。

### 生成に失敗した場合

見出しと定型文だけのキャプションになります。**空の本文は、他社の文章を貼るよりましです。** 記事ページの取得に失敗した場合はRSS要約を材料に生成します。

### オプション

```bash
python3 run_publish.py --no-body      # 本文を生成しない
python3 run_publish.py --no-article   # 記事ページを取得せず要約だけで生成
```

APIコールは選んだ件数分だけ発生します（1日1〜3件程度）。
