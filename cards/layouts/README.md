# REVO 投稿レイアウト（4種）

ニュースカードと同じデザインシステム（`#0A0A0B` / `#F5D547` / Saira Condensed + Noto Sans JP、左上のオブリークタグ、REVO+日付のフッター）を共有しつつ、**構造だけを変えた**4種類です。答える問いが違うので、形も違います。

| レイアウト | 用途 | コンセプト |
|---|---|---|
| `roadmap` | ロードマップ・進捗報告 | **シフトインジケーター** |
| `changelog` | 機能改善報告 | **整備記録簿** |
| `feature` | 機能紹介 | **パーツカタログの番号解説** |
| `events` | その月のイベント | **エントリーリスト** |
| `cover_events` | イベントまとめの**表紙** | **窓としての月数字** |
| `cover_feature` | 機能紹介の**表紙** | **ネームプレート** |

## コンセプトの意図

**roadmap — シフトインジケーター**
左から埋まっていくセグメントは、ドライバーが文字を読まずに状況を把握する見方そのものです。「どこまで進んだか」が一語も読む前に伝わります。完了は塗り、進行中は枠線のみ、未着手は暗いまま。セグメントの数と状態はフェーズ一覧から自動生成するので、バーと本文が食い違うことがありません。

**changelog — 整備記録簿**
車のオーナーは整備手帳を読み慣れています。日付があり、小さな項目が積み重なり、それぞれに作業種別のスタンプが押される。バージョン番号を走行距離の位置に置き、各行にスタンプを付けることで、リリースが「宣伝」ではなく「やった仕事」として読めます。スタンプを塗りつぶしにせず枠線にしたのは、アクセント色のブロックが並ぶと警告パネルに見えるためです。

**feature — パーツカタログ**
社外パーツのカタログは、英語で名前を出し、下に和名を置き、できることを①②③で示します。パーツを買ったことがある人には既に馴染んだ構造で、しかも機能紹介の文章を3つの具体的な主張に絞ることを強制します。

**events — エントリーリスト**
レースのエントリー表は、番号・名前・場所が並んだ日付順の名簿で、左端の日付を目で追って読みます。「今月どこに行けるか」を確認する動作と同じなので、日付列だけをディスプレイ書体＋アクセント色にして、他は静かにしています。月の数字を大きく取るのはここでは正当で、サムネイルサイズでも残るべき情報がそれだからです。

## 表紙（1枚目用）

`events` と `feature` は2枚目以降の中面です。カルーセルの1枚目には別の作りが要ります。**表紙が運ぶのは事実ひとつと指示ひとつ**（何月か／めくれ）で、残りは写真に任せます。背景画像は必須です。

**cover_events — 窓としての月数字**
月の数字を巨大に、しかも塗りではなく**輪郭だけ**で置いています。写真が数字を透かして見えるので、カード上で最も大きい要素でありながら最も邪魔をしません。左端で切れているのは意図で、中央に収めると仮置きに見えます。中面では同じ数字を小さく塗りで使うので、表紙と中面が同じ系列として繋がります。

**cover_feature — ネームプレート**
パーツは名前が打たれた箱で届きます。塗りのまま、端で切れて、腕を伸ばした距離でも読める。中面が「何ができるか」を説明する分、表紙は名前を刻むことだけをします。

**2つは意図的に逆にしてあります。** イベント表紙はディスプレイ書体を抜いて写真を透かし、機能表紙は塗って写真の上に乗せる。フィードに並んだとき、同じものだと誤認されないためです。

表紙ではフッターの日付を **SWIPE** に差し替えています。日付は本文に既にあり、表紙で伝えるべきは「めくれ」だからです。

```python
from layouts import render_cover_events, render_cover_feature

render_cover_events(
    month=9, count=4, area="首都圏・東海",
    photo="~/Pictures/daikoku.jpg", year=2026,
    date_str="2026-09-01", out="out/cover_events.png")

render_cover_feature(
    name_en="COLLECTION", name_ja="愛車のコレクション",
    hook="これまで乗ってきた車を、一台ずつ記録して並べておけます。",
    photo="~/Pictures/garage.jpg",
    date_str="2026-08-19", out="out/cover_feature.png")
```

`overlay`（既定 0.30）で黒スクリムの濃度を調整できます。明るい写真は 0.45 程度まで上げてください。

**英語名は1行に収まる長さに。** `cover_feature` のネームプレートは折り返さず自動で縮小します。長すぎると小さくなってネームプレートに見えなくなるので、10〜12文字程度までが目安です。

## 使い方

```python
from layouts import render_roadmap, render_changelog, render_feature, render_events

render_roadmap(
    period="Q3", period_label="2026年 第3四半期",
    phases=[
        {"text": "写真受け渡し機能のβ公開", "status": "done"},
        {"text": "実績・称号システムの実装", "status": "now"},
        {"text": "イベント連携の開放",       "status": "next"},
    ],
    date_str="2026-08-19", out="out/roadmap.png")

render_changelog(
    version="v1.4", when="8月アップデート",
    items=[{"tag": "NEW", "text": "..."}, {"tag": "IMP", "text": "..."},
           {"tag": "FIX", "text": "..."}],
    date_str="2026-08-19", out="out/changelog.png")

render_feature(
    name_en="COLLECTION", name_ja="愛車のコレクション",
    lead="これまで乗ってきた車を、一台ずつ記録して並べておける機能です。",
    points=["所有期間と仕様を車ごとに残せる", "手放した車も履歴として残る",
            "プロフィールから他のオーナーに見せられる"],
    date_str="2026-08-19", out="out/feature.png")

render_events(
    month=9, area="首都圏・東海",
    events=[{"day": "06", "wd": "SUN", "name": "...", "place": "..."}],
    date_str="2026-09-01", out="out/events.png")
```

全て `transparent=True` で背景透過PNGを出せます。

## 件数の目安

| レイアウト | 推奨 | 上限 |
|---|---|---|
| roadmap | 3〜5フェーズ | 6 |
| changelog | 3〜6項目 | 6 |
| feature | 3ポイント | 3（超過分は切り捨て） |
| events | 4〜6件 | 6（超過分は切り捨て） |

上限を超えると文字が縮んでフィードのサムネイルで読めなくなります。**1枚に詰めるより分けたほうが伝わります。**

## 実装上の注意

**リストの `min-height:0` を外さないでください。** リストは `flex:1 1 auto` で余白を埋めるようにしていますが、それだけだと内容に合わせて伸びてしまい、`clientHeight` が常に内容と一致するため縮小ロジックが発火しません。6件のイベントがフッターに重なる不具合がこれでした。

**ステータスラベルは4文字以内に。** `IN PROGRESS` は2行に折り返して、その行だけ列がずれました。`NOW` に変えています。

# ロゴ

`cards/brand/logo.png` を置くと、**全レイアウトのフッターが自動でその画像に差し替わります。** ファイルが無ければ Saira で組んだ `REVO` の文字にフォールバックするので、用意ができるまで止まりません。

背景透過PNG、横長の切り抜き、明るい色。高さ56pxで表示されます。詳細は `cards/brand/README.md`。

画像ロゴには傾きを掛けていません。タイプの `REVO` はストライプに合わせて `skewX(-11deg)` していますが、完成したロゴは固有の角度を持っているので、その上から傾けると意匠が歪みます。

# 週次の運用

毎週YAMLを1枚書いて1コマンド。写真もタイトルもそこで指定します。

```bash
cd cards
python3 weekly.py --init 2026-W36        # 雛形を作る
# posts/2026-W36.yml を編集、写真を photos/ に置く
python3 weekly.py posts/2026-W36.yml     # 全カードを書き出す
```

出力は `out/2026-W36/` に番号付きで並びます。

```
01_cover_events.png          ← 完成版
01_cover_events_overlay.png  ← 背景透過版
02_events.png
02_events_overlay.png
...
caption.txt
```

**posts の並び順がそのままカルーセルの順番**です。ファイル名の番号で固定されるので、アップロード時に順番を思い出す必要がありません。

## spec の書き方

```yaml
week: 2026-W36
date: 2026-08-31

posts:
  - type: cover_events
    photo: daikoku_night.jpg     # photos/ に置いたファイル名
    month: 9
    count: 4
    area: 首都圏・東海
    title: 今月のカーイベント     # 毎週ここを変える

  - type: events
    month: 9
    area: 首都圏・東海
    events:
      - {day: "06", wd: SUN, name: MOONEYES Sidewalk Sale, place: 横浜・本牧}

caption: |
  ここにキャプションを書きます。

hashtags: >
  #カーイベント #車好きと繋がりたい #REVO
```

使える `type` は `cover_events` / `events` / `cover_feature` / `feature` / `roadmap` / `changelog` / `news` の7つ。どれも同じspecに混ぜて並べられます。

`overlay` を各postに書けば、写真ごとにスクリムの濃度を変えられます。

## なぜファイルにしたか

タイトルと写真の選択は毎週変わり、しかも直したり使い回したりします。specがリポジトリにあれば、**書き出す前に直せて、書き出した後も残り、翌週にコピーして使える**。コマンドラインの引数で毎回打つ方式ではこれができません。

先週のspecをコピーして日付と中身を変えるのが、実際には一番早い運用になるはずです。

## エラーの出方

写真が見つからない場合と、`type` が未知の場合は、書き出す前にその場で止まります。半端に生成されたフォルダが残らないようにしてあります。

```
写真が見つかりません: cards/photos/nope.jpg
  photos/ に置いたファイル名を指定してください。
```
